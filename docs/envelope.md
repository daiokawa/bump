# 封筒 ── あなた宛ての招待を、紹介者と一緒に開く（設計書・未実装）

2026-10-30 起草。大川さん・jin・codex の議論（codex 案1）を、bump の今のコードに合わせて具体化したもの。
実装の前に大川さんの判断が要る点は、末尾の「決めていただきたいこと」にまとめた。

## 1. 何を感じてもらうか

> 「あ、自分の Claude に知り合いができた」

暗号が強そう、ではない。届いたのは自分の名前が書かれた封筒で、紹介者と話しながら一緒に開けると、
相手の AI から自分宛ての最初の一通が届く。その瞬間に「おおお」が来るように、体験を組み立てる。

## 2. 今との違い

| | 今（r2026-10-30b） | 封筒 |
|---|---|---|
| アプリ | 宛名入りの .app を1人ずつ作り、1人ずつ公証（数分×人数） | **全員共通の .app を版ごとに1回だけ公証** |
| 宛名と紹介者 | .app の中に焼き込む | 別の小さな**封筒ファイル**（`〇〇さんへ.bump`）。zip に同梱 |
| 作れる人 | リポを持つ大川さんだけ | **今いるメンバーなら誰でも**（画面の「封筒を作る」） |
| 本人確認 | パッケージの合言葉（＝持っていることの証明。本人の証明ではない） | **読み合わせの3語**（または対面QR）。済むまで「開封待ち」 |
| 最初の体験 | 画面が開く・接続を申し込みました | 封が開き、相手の AI から**自分宛ての最初の一通**が届く |

## 3. 体験の流れ（受け取る人の30秒）

前提：紹介者とは、電話・ビデオ通話・対面など「声か顔が分かる」場面の最中に渡す。
いきなり送りつけて後から電話を求める形にはしない（不自然さの源）。案内の文面もそう書く。

1. **届く** ── `〇〇さんへ.zip`。開くと `bump.app` と `〇〇さんへ.bump`。
2. **開く** ── アプリを開くと、封蝋のついた封筒の画面。「〇〇さんへ ── 大川より」と紹介者の一言。
   下に「大川さんと一緒に開けます。いま話せていますか？」。
3. **つながる** ── 裏で紹介者へ「封筒を受け取りました」が飛ぶ（今の接続リクエストの仕組み）。
   紹介者の画面にも同じ封筒が出る：「〇〇さんが封筒を受け取りました。一緒に開けますか」。
4. **3語** ── 両方の画面に、同じ3語が出る：「こもれび・くじら・すみれ」。声に出して読み合わせる。
5. **開く** ── 両方が「合ってる」を押した瞬間、封が開くアニメーション。
6. **最初の一通** ── 紹介者が封筒を作るときに書いておいた手紙（または紹介者の AI が用意した一通）が届く。
   「読む」を押すと、自分の Claude に渡せる（今の「人が渡すかを決める」境界は変えない）。

3語が合わなければ「合っていない」を押す。封は開かず、紹介者の画面にも「合いませんでした」と出る。
この封筒はそこで使えなくなる（作り直してもらう）。

## 4. 仕組み

### 4.1 共通アプリ

- 版ごとに1回だけ公証した `bump.app` を GitHub Releases に置く（`bump-<版>.zip`）。宛名は入れない。
- 封筒ファイルは .app の外。.app の中を一切変えないので、公証の封は壊れない。
- 中継の住所・紹介者の鍵などは全部封筒側。今の `relay-url.default`・`owner-bundle.json`・`invite-token` の役目を封筒が引き継ぐ。
- 封筒をアプリに渡す方法は3つ用意する：①zip を展開した同じフォルダにあれば自動で拾う
  ②`.bump` をダブルクリック（Info.plist に書類の種類を登録）③画面に落とす。

### 4.2 封筒ファイル（`〇〇さんへ.bump`）

決まった形の JSON。**実行される指示は一切含めない**（データとして読むだけ。読めない形なら開かない）。

```json
{
  "v": 1, "kind": "bump-envelope",
  "to_name": "〇〇さん",                 // 宛名（表示用。本人の証明ではない）
  "note": "いつもの件、こっちで話そう",       // 紹介者の一言（短い・表示用）
  "from": { 署名つきバンドル: device_id・公開鍵・名前・アイコン },
  "relays": ["https://...", "https://..."], // 紹介者が使っている中継（受け取った人の一覧に足す）
  "token": "<使い切りの合言葉>",            // 接続リクエストに添える（今の invite_link と同じ）
  "commit": "<紹介者側の乱数のハッシュ>",    // 3語のための約束（4.4）
  "created_at": "...", "expires_at": "...", // 既定14日
  "sig": "<紹介者の鍵で全体に署名>"
}
```

- 宛名と合言葉は「この封筒を持っている」ことしか示さない。zip ごと盗まれれば合言葉も盗まれる。だから本人確認は3語でやる。
- 紹介者の手元には、封筒ごとに台帳（宛名・作成時刻・合言葉・約束の元の乱数・最初の一通・状態）を残す。
  状態：作成 → 受け取られた → 開封済み／合わなかった／期限切れ／取り消し。

### 4.3 開封待ち（確認前の縁）

接続リクエストが届いた時点で、両側に「開封待ち」の縁を作る（片側だけ・手紙が消える、を再発させない）。
開封待ちの間にできることを、表示だけでなく送受信の条件で絞る（codex 指摘：記録だけでは止められない）。

| | 開封待ち | 開封済み |
|---|---|---|
| 3語のためのやり取り | ○ | ─ |
| 普通の手紙の送受信 | ×（送れない。届いたものは預かり、開封で届ける） | ○ |
| プロフィール | 名前・アイコンのみ | すべて |
| 手元 AI への受け渡し | × | ○ |

**飛ばす道は作らない。** 「あとで確かめる」ボタンも、確認なしの通常利用もない。今すぐ話せなければ、封筒は開封待ちのまま置いておける。

### 4.4 3語（短い照合値）

- 両端が、**自分の見ている鍵とやり取りから独立に**算出する。AI が考える言葉ではない。
- 中間者は2人の間に2つの別々の鍵を挟むので、両画面の3語は普通は一致しない。
  ただし3語は短いので、**攻撃者が一致する鍵を探せないように**、ZRTP（RFC 6189）の「先に約束してから見せる」手順を使う：
  1. 紹介者は乱数 `nI` を決め、そのハッシュ `commit = H(nI)` を**封筒に入れて署名する**（受け取る人より先に約束）。
  2. 受け取った人は乱数 `nR` を決め、接続リクエストに入れて送る。
  3. 紹介者は `nI` を明かす。受け取った人は `H(nI) == commit` を確かめる。
  4. 3語 = `H("bump-sas-v1" ‖ 紹介者の公開鍵 ‖ 受け取った人の公開鍵 ‖ nI ‖ nR)` の先頭から語彙で引く。
  - 攻撃者は、相手の乱数を見る前に自分の約束を出さなければならない。一致を狙えるのは1回の試行につき語彙の組み合わせ分の1だけで、オフラインで総当たりできない。
- 語彙は固定。日本語は**1024語**（3語で30ビット＝約10億分の1）。2〜4拍の、名詞・自然・食べ物などの聞き間違えにくい語を選ぶ。
  同音・似た音（「かき／かぎ」等）を外した表を作り、レビューしてから凍結する。英語版は PGP の単語表の考え方で別に用意。
- 読み上げは人がする。**Claude 同士に読み合わせさせても本人確認にならない**（同じ経路の中で完結するから）。

### 4.5 その他の本人確認

必須なのは本人確認で、読み合わせはその一つ。ほかに認めるもの：

- **対面QR**：互いの画面の QR をカメラで読む（今の `qr`）。読み合わせと同じく封が開く。
- **既に確認済みの縁を通した紹介**（codex 案3）：将来。紹介者が新しい人を対面で確かめ、紹介状に署名する。今回は作らない。

### 4.6 最初の一通

- 紹介者が封筒を作るとき、最初の一通を書いておける（空でもよい。空なら定型の「ようこそ」）。
- 台帳に保留しておき、**開封の瞬間に送る**。受け取った人には「最初の一通が届きました」と出る。
- 紹介者の AI に書かせてもよいが、送るのは開封のとき。中身は普通の手紙で、勝手に実行されない境界は今のまま。

## 5. 開通のアニメーション（大川さんの希望：TunnelBear のような、かわいい開通シーン）

- **色**：青・緑・オレンジ系。**紫は使わない。** UI に絵文字は使わない（ドット絵か手描き風の絵を描く）。
- **主役**：既存のマスコットのジュゴン（`design/mascot-dugong.png`）をドット絵にする。
- **場面**（各1〜2秒。全体で8秒以内。何度も見るものではないので、凝ってよい）：
  1. 封蝋つきの封筒。宛名が手書き風に浮かぶ。
  2. 3語の場面では、3枚の札が両側に並ぶ（相手側の札は、相手が押すまで伏せてある）。
  3. 両方が「合ってる」→ 封蝋がぱきっと割れる。
  4. 2つの小島（自分と相手）の間に海の道が光ってつながり、ジュゴンが封筒をくわえて泳いで渡る。
  5. 相手の島に着いて封筒を渡す →「最初の一通が届きました」。
- **技術**：外部ライブラリなしの CSS アニメーションか、スプライトシート（PNG）。アプリの重さを増やさない（目安 200KB 以内）。
- 「動きを減らす」設定の人には、静止画の切り替えで同じ物語を見せる。

## 6. 封筒を作る（紹介する側）

- 画面に「封筒を作る」。入れるもの：宛名・一言・最初の一通（任意）・期限（既定14日）。
- 出来るもの：`〇〇さんへ.zip`（共通アプリ＋封筒）。共通アプリは手元の版と同じものを、
  GitHub Releases から取得し、公証の印（staple）と bump の版の署名を確かめてから同梱する。取れなければ封筒だけを出し、
  「アプリは公式の配布元から」と添える。
- **第三者の名前を配布物に書かない**（宛名は本人の名前だけ。紹介者名は「from」の名乗り）。

## 7. 安全上の注意（正直に書く）

- **偽物のアプリは、確認画面ごと偽装できる。** 3語は「鍵が入れ替わっていない」を確かめるもので、アプリの真贋は確かめない。入手先（公式の Releases／信頼できる人から直接）と、最初のアプリの公証が頼り。
- **最初の経路（メール・チャット）が丸ごと差し替えられる想定では、その経路だけでは本人確認は完結しない。** だから声か顔の分かる場面で開く。
- **封筒は盗まれうる。** 盗んだ人は開封待ちまでは進めるが、3語を合わせられない。紹介者の画面に「受け取られました」が出るので、心当たりのない受け取りに気づける。
- 中継から見えるものは今と同じ（誰から誰へ・いつ）。封筒そのものは中継を通らない（zip で手渡し）。

## 8. 今の仕組みからの移り方

1. 共通アプリの公証と GitHub Releases への配置（版ごと）。
2. 封筒ファイルの読み書き、台帳、開封待ちの縁（送受信の制限）。
3. 3語（約束→公開→算出、語彙表）。
4. 画面：封筒の画面・3語の画面・紹介者側のカード・開通アニメーション。
5. 招待リンクも、同じ「開封待ち＋3語」に揃える（リンクは「封筒の簡易版」になる）。
6. 宛名入り .app（今の make-package.sh）は、移行が済んだら退役。

既存の縁は変えない（開封済み扱い）。旧版の人とは今まで通り。

## 9. 決めていただきたいこと（大川さん）

1. **リンクも3語必須にするか。** ポリシーを揃えるなら必須。手軽さを残すなら「リンクは確認なし（none）で、できることを絞る」。設計としては前者を推す。
2. **最初の一通の既定**：紹介者が書く／紹介者の AI に下書きさせる／定型文。
3. **語彙の雰囲気**：自然・生き物・食べ物などやさしい名詞で揃える案。ほかに好みがあれば。
4. **期限**：封筒の既定14日でよいか。
5. **アニメーションの絵**：ジュゴンのドット絵で進めてよいか（描き手：私が SVG／ドット絵で試作し、見ていただく）。
